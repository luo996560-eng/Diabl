# 《時空武林》發展藍圖

本文件把七點方向拆成可交付的階段，並標明每一階段的技術限制與需要決策的地方。原則：不刪減任何既有功能，新東西一律疊加；每一步都要能上線、能玩、能回饋。

## 全貌

| 方向 | 終點 | 目前狀態 |
| --- | --- | --- |
| 1 事件與選項由鈕釦產生、自由對答判定善惡 | 玩家自由說話決定事件走向，鈕釦判定後發獎勵 | 第一版已上線：自由回應 → 鈕釦判定 → 對應既有選項 |
| 2 鈕釦逐步擴充、模組化、可部署 | 判定模組可獨立測試、版本化、可替換 | 已有 16 個 core 模組與 pack 載入器，本次新增判定模組與測試 |
| 3 反爬蟲、反外掛、檔案加密，且不影響正常遊玩 | 靜態前端能做的最大化防護 + 伺服器端裁決 | 已有「武林守衛」；加密與線上裁決需後端 |
| 4 大量水墨畫素材 | 寵物 50、妻子 100、其餘 20–30、場景介面功法全套 | 已有 13 幅場景、裝備與功法程序化水墨圖、27 幅師父肖像 |
| 5 既有功能不刪、要優化與修錯 | 每次改版都更穩 | 已建立可重複執行的整局回歸測試 |
| 6 鈕釦要真的聽懂，不得已讀亂回 | 判定有依據、有信心、不確定時承認不確定 | 自由回應已內建「無關就不判定」與信心門檻 |
| 7 轉為可同時在線、可聊天的網路遊戲 | 多人同服 + 聊天 | 靜態 Pages 無法承載，需選後端 |

## 第 1 點：事件由鈕釦掌控

### 已上線（v27.5）
- 事件畫面新增「鈕釦自由回應」：玩家用自己的話寫行動，`core/niukou-choice.js` 判定善／中立／惡，再對應到同一事件中同路徑的既有選項，效果與獎勵完全不變。
- 三種結果：
  - 有明確行動線索且信心足夠 → 套用對應抉擇，並顯示判定依據、信心百分比與對應的抉擇文字。
  - 信心不足 → 不動遊戲狀態，只說明不確定的原因。
  - 與事件無關 → 直接拒絕（`no-signal`），不推進月份，避免「問 A 答 B」。
- 否定語境有處理：「不救他」不會被當成善行。

### 下一階段
1. 把判定從「關鍵詞＋相似度」升級為「意圖＋對象＋手段」三欄位：誰、做什麼、怎麼做。這樣「搶走他的包袱」與「搶回自己的包袱」才分得開。
2. 選項產生：以事件情境（31 類）為主幹，用鈕釦組裝 2 正 1 中 2 邪的選項文案，先與現有 2,400 則並存比對，人工驗收後才替換顯示。
3. 獎勵發放改由判定結果直接計算：目前沿用既有選項的數值，未來改成依「動機純度 × 手段代價」給分，並保留現行數值作為上限校準。
4. 隱藏標籤（薛定諤）與自由回應的關係：自由回應一律先判定再揭曉，不預先顯示善惡。

### 風險
- 純前端判定必然可被繞過（改記憶體、改判定結果）。真正的「零失誤」需要伺服器端判定，屬於第 7 點的後端工作。

## 第 2 點：鈕釦的模組化與部署

現況：`core/` 有 16 個模組，`packs/` 有 17 份 JSON 內容包（含雜湊校驗），`tools/update-manifest.mjs` 管雜湊。本次新增：

- `core/niukou-choice.js`：純函式、無遊戲狀態依賴、可單獨 `node --test`。
- `tests/niukou-choice.test.mjs`：8 項判定回歸測試。
- `tests/game-smoke.test.mjs`：以真實 `index.html` 啟動，跑整局流程。

後續模組化順序：
1. 判定層與詞庫層分離：`niukou-choice` 只留演算法，語料移到 `packs/`，讓新增語料不必改程式。
2. 版本協商：每個模組宣告 `version` 與 `requires`，載入器檢查不相容時降級而非崩潰。
3. 部署：`tools/` 增加 `build-assets` 與 `verify-deploy`，把素材與程式分開快取。

## 第 3 點：反外掛與加密

### 靜態前端能做到的
- 既有的「武林守衛」：偵測主控台改值、替換核心函式、自動化瀏覽器、模擬點擊、注入腳本、竄改計時器、手改存檔與積分；三次累計後停用排行榜。
- 存檔簽章（`wgSignSave`）與備份輪替。
- 事件判定加入伺服器端種子後，同一月份的結果不可重抽。

### 靜態前端做不到的（必須說清楚）
- 檔案加密：`index.html` 與 `core/*.js` 一定要送到瀏覽器才能執行，任何「加密」都只是延遲閱讀，不能真正保密。能做的是混淆與分片延遲載入，收益有限。
- 反爬：GitHub Pages 沒有辦法封鎖特定 User-Agent 或加驗證。真正的反爬要放在 CDN 或反向代理層。
- 反外掛：客戶端判定永遠可被繞過。

### 建議
- 遊戲邏輯與存檔裁決搬到後端（第 7 點），前端只做顯示。這一步做完，第 3 點才算真正成立。
- 過渡期：把「排行榜成績」與「輪迴積分」改為伺服器簽發，其他本機數值不管，避免為了防弊犧牲單機體驗。

## 第 4 點：水墨素材

### 現有
- 13 幅場景水墨、裝備依部位與意象程序化生成、功法卷軸、27 位神話師父肖像。

### 目標與做法
- 寵物 50 張、妻子 100 張、首領與山賊等龍套各 20–30 張。
- 建議以「素材包 + 清單」管理：
  - `assets/ink/pet/001.webp` … `050.webp`
  - `assets/ink/wife/001.webp` … `100.webp`
  - `assets/ink/foe/shanzhai/01.webp` …
  - `assets/ink/manifest.json` 記錄每張的題材、尺寸、授權與適用標籤。
- 圖片應為 WebP、長邊 512–768、單張 40–90 KB，總量控制在 15 MB 內，並以 `<img loading="lazy">` 與「先文字後補圖」的方式載入，避免拖慢手機。
- 輪替規則：以存檔內的固定種子取模，同一角色不會每次刷新都換臉；妻子依 `id` 綁定，寵物依 `species+stage` 綁定。

### 待決策
- 由我生成（需先確認可接受的畫風與授權），或你提供圖庫後我接線。兩者都能做到，但管線不同。

## 第 5 點：優化與修錯

已建立兩層防護：
- `tests/game-smoke.test.mjs`：真實頁面啟動、事件、自由回應、600 個月連續遊玩、數值合法性。
- 既有的 pack、認知、情緒、學習、指南測試。

待修清單見 `docs/audit-2026-11-27.md`。最高優先是把「事件中重新整理會重抽事件」修掉。

## 第 6 點：真的聽懂

已落實的紀律：
- 沒有行為線索就不判定（回「請說清楚」），不硬猜。
- 有信心門檻（0.42），低於門檻就不執行。
- 判定結果一定附依據與信心，玩家可自行判斷是否被誤判。
- 否定、雙重否定、轉折已有處理；下一步加入「對象」與「手段」拆分，處理「打他」與「打醒他」。

## 第 7 點：線上化與聊天

靜態 GitHub Pages 只能托管檔案，沒有伺服器、沒有資料庫、沒有 WebSocket。要多人同服必須選一個後端。

| 方案 | 優點 | 缺點 | 適用 |
| --- | --- | --- | --- |
| Supabase | Postgres + Realtime + Auth 一次到位，前端 SDK 直接接，免費額度足夠起步 | Realtime 是廣播式，複雜回合制要自己寫規則；尖峰會有延遲 | 最快上線 |
| Cloudflare Durable Objects | 每個房間一個物件，天生適合回合制與聊天室；延遲低 | 需要 Workers 專案與付費方案，學習曲線高 | 長期正解 |
| 自架 Node + WebSocket | 完全掌控 | 需要主機、備份、監控、憑證 | 有維運能力時 |

建議路徑：
1. 先把存檔與排行榜搬到 Supabase，單人存檔雲端化（不影響現有本機存檔）。
2. 加聊天室（Realtime broadcast），先做世界頻道與私訊。
3. 再做「同時在線的江湖」：共享事件、勢力戰、拍賣行跨玩家。
4. 最後把事件判定搬到伺服器，完成第 3 點的防弊。
